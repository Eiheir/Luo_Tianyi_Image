# 智能图床管理器 · 独立部署说明

> 本模块（`manager/`）为「洛佬の美图」图床的**独立扩展**，全部代码存放在独立的 `manager/` 目录内，
> **未修改、未移动、未删除**原有图床的任何文件、目录层级与配置。原有图床业务不受任何影响；
> 本模块可随时整体删除（删除 `manager/` 目录即可）而图库照常工作。

---

## 一、功能总览

| 功能 | 说明 |
| --- | --- |
| 批量上传 | 拖拽 / 点选 / **剪贴板 Ctrl+V 粘贴**多文件（单批最多 200 个，单文件 ≤ 60 MB），**逐文件串行提交**：实时进度、单张失败可重试、中途可停止 |
| 自动分类归档 | 按《图片命名规则》：近方形→avatar，横图→`wallpapers&illustration/heng`，竖图→`shu`，表情包→`emoticon/<主题>/`，临时→`temporary`；误分类可批量**移动到其他分类**（自动续排编号，失败整批回滚） |
| 重复图片智能检测 | 字节级 MD5 精确查重 + dHash 感知指纹相似检测（汉明距离阈值可配置），完全重复自动跳过，相似仅提示不拦截；查重面板支持**「保留最高清」一键清理**（自动保留组内像素面积最大的一张）与**「忽略本组」**（确认只是画风相似后，这些图片彻底退出相似归组、不再提示，其他图片之间的提示不受影响；可随时取消；忽略记录存于 `.cache/dedup-ignore.json`，移动/规整/改名后自动清理失效记录） |
| 格式自动转换 | 支持 jpg/jpeg/png/gif/bmp/webp/avif；上传时自动 EXIF 转正、可选转 WebP/JPEG 压缩、清除元数据防隐私泄露。动图默认原样保留；「保留原格式」且无需转正、勾选剥离时不含 EXIF 的图片，按**原始字节**保存、不做任何重编码 |
| 访问链接批量生成与导出 | jsDelivr 主站 / **Fastly、Cloudflare、Gcore 镜像** / GitHub Raw 五种格式界面随时切换；复制可选纯链接 / Markdown / HTML / BBCode；支持导出 txt / json / csv / markdown（CSV 含 BOM，Excel 直接打开不乱码）；中文路径自动 URL 编码 |
| 图片库管理 | 目录树 + 分类/格式/**文件大小/像素宽度**筛选、序号/时间/体积排序、**灯箱大图预览（←/→ 连续浏览、Esc 关闭、就地复制/删除）**、批量多选操作、**目录编号规整**（消除删除空洞，旧链接失效需确认）、**表情包主题改名** |
| 存储空间可视化统计 | 各分类数量、体积、编号使用进度，环形图展示；**近 12 个月新增趋势** |
| 回收站 | 软删除可恢复；条目**缩略图预览**；单条/整批恢复；**恢复时目标编号被占自动改号**（绝不覆盖同号新图）；**彻底删除（不可逆）**；**30 天过期批次启动时自动清理** |
| 便捷操作 | 自定义表情包主题名、Git 一键同步（**同步前自动 pull --rebase**，多机使用更稳；可选同步后刷新 jsDelivr 缓存）；**图形化设置面板**（质量/批量上限/查重阈值/默认链接格式，写入 config.json 白名单字段） |

## 二、接入方式

### 方式 A：exe 免安装运行（推荐，无需 Node.js 环境）

1. 将 `manager/dist/LTY-图床管理器.exe` 复制到**仓库根目录**（与 `LTYpicture` 文件夹同级）：

   ```
   仓库根/
   ├── LTY-图床管理器.exe    ← 放这里
   ├── LTYpicture/           ← 原有图库，不做任何改动
   └── ...
   ```

2. 双击运行。首次运行会在 exe 旁自动生成 `config.json`（`repoRoot` 已自动设为 `.` 指向当前目录）、`.cache/`（索引与缩略图缓存）、`.trash/`（回收站）。
3. 浏览器访问提示的地址（默认 <http://127.0.0.1:3210>）即可使用。
4. 关闭窗口或结束进程即停止服务；再次双击即可重启。

> exe 必须与 `LTYpicture` 同级放置，否则图库定位不正确。

> **就地运行变体**：若不想把 exe 移出 `manager\dist\`，也可以直接在原处双击运行，
> 但首次运行后需打开 exe 旁生成的 `config.json`，把 `"repoRoot": "."` 改为 `"repoRoot": "../.."`
> （从 `dist` 出发上一级是 `manager`，再上一级才是仓库根），保存后重启 exe 即可正确识别图库。

### 方式 B：源码运行（需要 Node.js ≥ 18）

```bat
cd manager
npm install
npm start
```

源码模式下通过 `../config` 相对定位，图库自动指向仓库根的 `LTYpicture`。

### 端口说明

默认监听 `127.0.0.1:3210`（仅本机访问）。若端口被占用，服务会自动从 3210 起逐个递增重试（最多 10 次），并在启动横幅中显示实际地址。可修改 `config.json` 的 `port` / `host` 后重启生效。

## 三、界面使用说明

- **上传视图**：拖拽文件到虚线框（或点击选择），可填写表情包主题名（仅对表情包生效）；实时显示每个文件的处理结果（归档路径、编号、是否转换、是否重复跳过、相似提示）。
- **图片库视图**：按分类筛选；点击图片查看大图与多格式链接（Markdown / HTML / BBCode / 原始 URL），一键复制；勾选多张可批量复制链接、移动分类、删除（进入回收站）。
- **统计视图**：各分类图片数量与体积、编号使用进度、存储占比环形图。
- **顶栏**：链接格式切换（jsDelivr / raw）、Git 同步状态徽标、「同步到 GitHub」按钮（手动提交模式，见第五节）。
- **回收站**：删除的图片软删除至 `.trash/<批次>/` 并记录精确路径，可在回收站面板一键恢复原位。

## 四、链接与 CDN 生效说明

生成的 jsDelivr 链接形如：

```
https://cdn.jsdelivr.net/gh/Eiheir/Luo_Tianyi_Image@main/LTYpicture/<分类>/<文件名>
```

- 链接在**图片通过 Git 推送到 GitHub 之后**才会生效，jsDelivr 有 **1~5 分钟** CDN 缓存延迟，属正常现象。
- 新上传的图片在推送前，本地图库内已可见（管理界面不依赖 CDN）。

## 五、Git 同步（手动提交模式）

- 上传落盘**不会**自动提交或推送，避免误操作直接公开未确认的图片。
- 确认无误后点击顶栏「同步到 GitHub」，服务会依次执行：`git add`（仅限定图库目录）→ `git commit` → `git push`。
- 同步仅操作图库目录内的文件，不会触及仓库其他路径；单步超时 120 秒，失败不影响已落盘文件，可修正后重试。
- 要求运行环境中已配置好该仓库的 git 凭据（如已安装 Git 并登录过 GitHub）。

## 六、配置项说明（config.json）

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `port` / `host` | `3210` / `127.0.0.1` | 监听端口与地址（仅本机） |
| `repoRoot` | 源码态 `..`，exe 态 `.` | 仓库根相对路径（exe 首次生成时自动修正，无需手改） |
| `imageRoot` | `LTYpicture` | 图库目录名（相对 repoRoot） |
| `repo.owner/name/branch` | `Eiheir` / `Luo_Tianyi_Image` / `main` | 用于拼链接；未显式配置时会从 git remote 自动探测兜底 |
| `classify.avatarRatioMax` | `1.2` | 长边÷短边 ≤ 1.2 判为近方形（avatar） |
| `dedup.hammingThreshold` | `5` | dHash 汉明距离阈值，越小越严格 |
| `dedup.onExactDuplicate` | `skip` | 完全重复的处理方式（跳过） |
| `upload.maxBatchFiles` / `maxFileMB` | `200` / `60` | 单批数量与单文件体积上限 |
| `upload.quality` | `100` | 转 WebP/JPEG 时的压缩质量 |
| `git.enabled` / `timeoutMs` | `true` / `120000` | 是否启用同步按钮 / 单步超时 |
| `git.purgeCdn` | `false` | 同步成功后逐文件请求 `purge.jsdelivr.net` 刷新 CDN 缓存（覆盖旧路径时有用；纯新增文件的链接本来就是冷的，默认关闭） |
| `linkFormat` | `jsdelivr` | 默认链接格式：`jsdelivr` / `fastly` / `testingcf` / `gcore` / `raw`（界面可随时切换） |

## 七、exe 打包方法（维护者参考）

打包依赖 `@yao-pkg/pkg`，其基础 Node 二进制（官方 patched 版）默认从 GitHub 下载，国内网络易失败，**需先预置缓存**：

> 注意：必须使用 yao-pkg 官方 patched 二进制。npmmirror 上的原版 `node.exe` 哈希与 pkg-fetch 内置的期望值不符，校验失败后会被自动删除并回退联网下载。校验算法为 **SHA256**。

```bat
:: 1. 预置 pkg 基础二进制（一次性，缓存目录按 pkg 版本为 v3.6）
::    直连 GitHub 失败时，可在完整 URL 前加镜像前缀（如 https://gh-proxy.com/）
curl -L -o "%USERPROFILE%\.pkg-cache\v3.6\fetched-v24.20.0-win-x64" ^
  "https://gh-proxy.com/https://github.com/yao-pkg/pkg-fetch/releases/download/v3.6/node-v24.20.0-win-x64"

:: 2. 校验 SHA256（pkg-fetch 3.6.6 对 node-v24.20.0-win-x64 的期望值）
certutil -hashfile "%USERPROFILE%\.pkg-cache\v3.6\fetched-v24.20.0-win-x64" SHA256
:: 期望值：a71b32eeff62d1fbddcd7ee63e9898580fe2e1d749db6734c3a6314b43890ed1

:: 3. 在 manager 目录执行打包
cd manager
npm run build
```

产物输出至 `manager/dist/LTY-图床管理器.exe`（单文件约 98 MB，内含 Node 运行时与 sharp 图像内核，目标机无需任何依赖）。打包脚本内置 Node 24/22/20 目标自动降级，兼容不同缓存版本。

## 八、异常处理与零影响保证

1. **独立目录**：本模块所有文件（含依赖、缓存、回收站）均在 `manager/` 内，运行时对图库只做「新增图片」与「用户主动执行的移动/删除」两种操作。
2. **路径防护**：所有来自前端的路径参数强制校验在图库根目录内，杜绝路径穿越（恶意路径返回 400）。
3. **进程级兜底**：未捕获异常/ promise 拒绝仅记录日志不退出；端口占用自动换端口；单文件处理失败只隔离该文件并回报错误，同批其余文件不受影响。
4. **原子操作**：配置写入、索引写入、图片落盘均先写临时文件再改名，断电/中断不产生半截文件。
5. **可随时退役**：停止进程并删除 `manager/` 目录即完全移除本模块，图库与原有业务零残留。

## 九、日常维护提示

- **回收站不是自动清理的**：`.trash/` 会累积，确认不再需要恢复后，可手动删除其中旧批次文件夹。
- **缓存可随时重建**：`.cache/`（查重索引、缩略图）可整体删除，服务会在下次访问时自动重建（首次会稍慢）。
- **修改配置后需重启服务**生效。
